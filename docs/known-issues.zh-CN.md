### ISSUE-003：一次性决定进入长期偏好

**类型**：缺陷 · **范围**：事实提取、画像 · **优先级**：P1 · **状态**：待决策

#### 现象与影响

原文只表达“本次部署决定使用关键词检索”，提取结果却可能被标为 `user / prefers / keyword retrieval`，进入正式画像。一次性的方案选择因此可能在之后的问答中被当作长期偏好使用。

会话结论中保存了正确的 decision，不会自动校正另一条 prefers 事实；两条写入路径需要保持含义一致。

#### 原因与证据

`LLMExtractor.facts_from()` 接受模型给出的关系类型，画像构建再根据 prefers 等关系归类，当前路径没有再次判断原文的场景限制。合成复现证明的是“给定这样的提取结果会进入偏好”，尚未测量真实模型发生误判的频率。

默认 `remember(..., scope="auto")` 会先进行瞬态路由。“本次部署决定使用关键词检索。”中的“本次”命中瞬态标记，合成端到端调用返回 `scope=working`，长期事实数量为 0。给定提取结果的复现不代表所有默认写入都会进入画像；显式 long、导入以及未命中瞬态标记的表述需要分别验证。

#### 处理要求

- 先确定一次性决定、长期采用规则和个人偏好的区分标准，再选择提取约束或画像筛选方案。
- 保留用户明确表达的长期技术偏好，不能把所有技术方案或单次提及一律排除。
- 如需修正已有事实，应保留原文、来源和变化历史，避免通过批量删除或改写关系掩盖误判。

#### 验收标准

- 明确偏好、限定场景的决定、长期工作规则及混合表达能够分别处理。
- 分别覆盖默认 auto 路由、显式 long、导入和未命中瞬态标记的表述，区分写入路由与提取器的判断责任。
- 同一原文产生的会话决定与画像事实在主体、适用范围和时间上不矛盾。
- 用户手动设定、跨会话确认的信息及明确的长期偏好不被误删或降级。

**代码与证据**：[提取器](../mnemotrace/consolidate/llm_extractor.py)、[画像构建](../mnemotrace/consolidate/structured.py)、[合成复现](#evidence-issue-003)。

### ISSUE-004：问答证据过宽且跨层重复

**类型**：缺陷 · **范围**：检索、证据组装 · **优先级**：P1 · **状态**：待处理

#### 现象与影响

询问“我不喜欢吃什么”时，上下文可能同时包含同一空间内其他人物的饮食偏好、住址、摄影计划或技术方案。同一条信息还可能在画像、事实、偏好表、摘要和原文中重复出现。

这些材料实际进入答题模型的输入；仅折叠界面卡片不会减少模型收到的内容。问题影响证据范围与信噪比，实际准确率变化尚未量化，也没有据此确认跨命名空间泄露。

#### 原因与证据

- 画像：默认加入当前叙事画像，未按本轮问题筛选其内部内容。
- 事实：混合检索返回排序靠前的候选，该返回位置缺少统一的最低问题相关性要求。
- 偏好表：以偏好关系、词项相关性和日期组织候选，人物与主题限定不足。
- 组装：各层局部去重不能保证同一信息在所有证据层之间只表达一次。

依据包括上下文估算样本和上述代码路径，尚无完整修复前后对照实验。界面中的上下文与原始对话 token 估算覆盖范围不同，不是实际计费量；原文片段数量也不限制整份证据上下文。

#### 处理要求

按问题所问的人物、主题、关系和时间选择证据，相关性不足时不为凑数量补入材料。减少重复时保留必要的原文、来源和限定条件，继续使用事实与原文的混合证据。

#### 验收标准

- 覆盖本人、明确询问他人、混合人物及混合主题的问题，证据归属清楚。
- “不喜欢番茄”与“喜欢番茄炒蛋的味道”等限定表达不被误合并或截掉条件。
- 简单问题减少无关与重复证据，多跳、聚合、时间更新和无答案场景仍保留所需材料。
- 比较实际选入的证据、答案正确性和统一口径的上下文估算，不以“必须短于原始对话”为唯一目标。

**代码与证据**：[证据组装](../mnemotrace/memory.py)、[混合检索](../mnemotrace/retrieve/hybrid.py)、[样本边界](#evidence-issue-004)、[已有调用链验证](../results/chinese_prompt_context_validation.md)。

### ISSUE-005：会话结论同义改写后重复保存

**类型**：缺陷 · **范围**：会话结论 · **优先级**：P1 · **状态**：待决策

#### 现象与影响

同一会话没有新增原文，反复总结时，模型仍可能用不同措辞重述同一结论，并新增为另一条 Fact，导致重复存储与统计膨胀。

重复总结也可能发现原文中此前遗漏的另一项决定或经验，因此不能把“第二次新增”一律当作重复，也不能直接禁用重复总结作为完整修复。

#### 原因与证据

每次关闭会话都可能重新调用模型分析整个会话。跨调用去重主要比较同用户、同会话、当前有效结论的小写 statement 前 120 个字符，why 不参与键，也不判断语义等价。

假模型的合成复现得到新增数量 `[1, 1, 0]`：前两次同义改写各新增一条，第三次文字完全相同则被拦截。现有相同文字回归不能证明真实模型改写时也能去重。

SDK 的 CloseSessionResult 注释承诺“未变更的会话重复关闭不会新增”，Journal 的注释也将重复蒸馏称为无害空操作。这些保证超出当前去重能力，需要与实际行为保持一致。

#### 处理要求

- 明确允许重复总结补漏，还是只在原文变化后再次提炼，并说明这对漏提取信息的影响。
- 区分相同文字、同义重复、真正补充和时间变化；相近但矛盾的结论不能合并。
- 保留手动修正、来源和双时间历史。原文追溯入口由 [ISSUE-009](#issue-009) 单独验收。
- SDK、页面说明和代码注释准确描述重复关闭的行为，不将文字去重表述为完整的会话级幂等保证。

#### 验收标准

- 覆盖相同回复、同义改写、前缀相同但含义不同、真正新增及原文增长。
- 不同主体、不同时间或相互矛盾的结论不会被误合并。
- 手动编辑过的结论不会被重新生成的旧措辞覆盖，来源记录保持完整。
- 重复关闭的公开契约、界面说明与实际新增数量一致。

**代码与证据**：[结论提取](../mnemotrace/consolidate/outcomes.py)、[关闭会话](../mnemotrace/service.py)、[SDK 契约](../clients/typescript/src/types.ts)、[结论页面](../frontend/src/pages/Journal.tsx)、[合成复现](#evidence-issue-005)。

### ISSUE-006：分类关键词误匹配

**类型**：缺陷 · **范围**：分类、画像 · **优先级**：P2 · **状态**：待处理

#### 现象与影响

事实标签和画像偏好分组会因局部字串命中而分错类别，影响管理筛选与阅读。已合成复现的样例包括：

| 路径 | 输入 | 当前分类 | 误命中 |
|---|---|---|---|
| 事实分类 | uses / storage engine | 身份 | storage 中的 age |
| 画像分组 | prefers / team collaboration | 饮食 | team 中的 tea |
| 画像分组 | prefers / 整理资料 | 饮食 | 料 |
| 画像分组 | prefers / 流行的编程框架 | 音乐 | 流行 |
| 画像分组 | prefers / 保留事实和原始会话片段 | 影视 | 片 |

#### 原因与证据

两套分类主要使用子串判断，英文缺少词边界，中文含单字或歧义词，并按固定顺序采用首个命中的类别。事实分类会保存为 Fact.category，画像分组则从关系与宾语临时计算，两者不能只修其中一处。

这些案例没有删除事实，也不证明存在隐私过滤或检索故障。敏感标记虽有相似匹配方式，仍需用独立样例核验。

#### 处理要求

收紧中文单字、歧义词和英文词边界，明确多类别命中的优先级。分类证据不足时允许回退“其他”，不强行增加类别；同时明确已有分类与手动覆盖的更新策略。

#### 验收标准

- 上述误判全部有回归，正常领域、复合关系和 favorite_ 等关系仍可识别。
- 分别验证持久化 Fact.category 与画像派生分组，修复范围不混淆。
- 不静默覆盖用户指定类别，不改写事实正文、来源和时间历史。

### ISSUE-007：画像待确认候选入口不可达

**类型**：缺陷 · **范围**：画像 · **优先级**：P2 · **状态**：待决策

#### 现象与影响

画像页面已经有待确认候选列表，以及确认、删除操作，但正常画像构建流程不能产生候选，因此这些入口无法正常出现。缺口位于候选进入规则，不等同于全部确认或删除功能缺失。

#### 原因与证据

画像先要求 `_polarity(predicate)` 有结果，才判断偏好是否已确认；`_confirmed()` 对相同条件又直接返回 True，因此该路径中的 tentative 分支不可达。此判断不读取 Fact.confidence。

合成测试中，置信度为 1.0 和 0.3 的给定偏好均进入正式画像。这证明分组路径的限制，不证明真实模型已经产生弱推断。

#### 处理要求

- 明确哪些信息属于用户直接陈述，哪些属于待确认的弱推断，再决定接通候选或调整能力说明。
- 不因只出现一次就把明确偏好降为候选，也不把来源数量或检索强化直接当作语义置信度。
- 明确确认与删除的持久化语义：当前确认会新增用户断言，删除会删除对应事实，均不只是切换界面标签。

#### 验收标准

- 覆盖明确偏好、弱推断、手动设定及重复来源，候选进入规则与说明一致。
- 确认、删除后的列表、统计和重启状态一致，不意外形成重复的用户断言。
- 候选分层不隐式过滤正常记忆检索，也不影响独立的记忆冲突处理入口。

**代码与证据**：[画像构建](../mnemotrace/consolidate/structured.py)、[画像页面](../frontend/src/pages/Profile.tsx)、[合成复现](#evidence-issue-007)。

### ISSUE-008：长期连接地址缺少选择与说明

**类型**：改进 · **范围**：接入配置 · **优先级**：P2 · **状态**：待处理

#### 现状与影响

接入命令的 API 地址默认来自 VITE_API_BASE，未配置时使用页面来源。通过开发页面接入时，保存的地址可能是 `http://localhost:5173`，形成“连接器 → Vite → 记忆服务”的长期依赖。

开发代理目前可用，不能仅凭端口号认定接入错误。风险在于关闭或更换 Vite 后，后端即使仍运行，已保存该地址的连接器也可能无法访问；这一停止代理场景尚未实测。

自动导入入口只生成 `mnemotrace-watch --install`，未传入当前服务地址或凭据。首次使用且没有环境变量或 watcher key 文件时，不能完成目标配置；已有 watcher 配置时，也不能保证导入当前页面所指的服务与空间。不能把 Codex MCP 已配置成功等同于 watcher 已使用相同目标。

Windows 的自动 scheduler 选择会落到 cron，当前没有 Windows 任务调度实现。界面提供 PowerShell 接入命令，不代表这条自动导入命令也已支持 Windows。

#### 现有依据

Settings 将 apiBaseUrl() 交给安装命令生成器，连接器会持久保存传入地址。页面没有独立选择目标 API 地址的入口；当前服务健康状态也不能代替对另一个自定义目标的验证。

watcher 的 `_URL_DEFAULT` 来自环境变量或本机 8000 端口，`_resolve_key()` 读取参数、key 文件或环境变量；这条安装路径不从 Codex MCP 配置继承目标。依据为命令生成与解析调用链，实际安装和调度仍需验收。

#### 处理要求

- 展示命令目标地址及其来源，允许单独填写连接器地址，不意外改变控制台自身请求的服务。
- 本机直连使用实际后端监听地址；远程部署使用连接器所在电脑可访问的地址。localhost 指向运行连接器的电脑，不能一律硬编码为 8000。
- 修改地址后同步更新 PowerShell、Bash 与复制内容，说明自定义目标是否已经验证。
- 自动导入命令明确目标地址、凭据来源与支持平台；执行前可核对其与当前空间的关系，不静默复用另一目标的配置。

#### 验收标准

- 覆盖开发代理、同源部署、显式 VITE_API_BASE 和自定义远程地址。
- 地址格式、命令参数转义和两种终端的复制结果正确，测试不记录真实 key。
- 在后端持续运行时，直连配置不依赖 Vite；页面健康检查不能把不可达目标显示为已通过。
- 覆盖无既有配置、已有其他目标、环境变量覆盖和 Windows 场景；没有可用调度器时明确说明，不把打印 cron 行当作已完成自动导入安装。

**代码与证据**：[接入页面](../frontend/src/pages/Settings.tsx)、[命令生成](../frontend/src/lib/codexSetupCommand.ts)、[地址选择](../frontend/src/lib/api.ts)、[watcher 目标与 scheduler](../mnemotrace/connectors/watch.py)。

### ISSUE-011：时间线缺少筛选与时间语义

**类型**：改进 · **范围**：时间线 · **优先级**：P2 · **状态**：待处理

#### 现状与影响

时间线目前已显示当前/历史状态及 supersedes 的“更新”标记，主要按 valid_at 展示事实。缺少人物、属性和日期筛选，也缺少可展开的完整替换链与明确的日期含义。

- 日期标注区分世界有效时间与系统得知时间，缺失值有明确回退，不把同一字段解释成多种时间。
- 覆盖 500 条及以上数据，事实与原始对话均能到达末页；没有重复、漏项或永远可点但不增长的加载按钮，筛选变化后正确重置分页。

### ISSUE-013：CSP 脚本授权、历史凭据清理与使用提醒待完善

### ISSUE-014：图谱截断后过滤导致当前关系缺失

**类型**：缺陷 · **范围**：图谱查询、展示 · **优先级**：P2 · **状态**：待处理

#### 现象与影响

“仅当前”开启时，历史关系可能先占满查询上限，使仍有效的关系不进入返回结果，页面显示没有符合条件的图谱或缺少部分当前关系。

#### 原因与证据

GraphPage 始终请求 `live_only=false, limit=120`，随后由浏览器过滤当前关系。后端 graph_data 收集到 120 条边便停止；在截断集合上本地过滤，不等价于在完整集合中过滤后再取 120 条。

合成数据含 121 条历史关系和 1 条当前关系时，该查询返回 120 条历史边，前端过滤后为 0；服务端使用 `live_only=True` 时返回 1 条当前边。

#### 处理要求

在保持开关切换时布局稳定的前提下，通过分页、调整返回协议或在正确筛选范围内执行上限，保证当前关系不会被历史关系挤出。若结果并不完整，应明确显示范围，不能把截断后的空集解释为整个空间无匹配数据。

#### 验收标准

- 覆盖超过 120 条历史关系、当前与历史交错、搜索及敏感过滤组合，当前关系可正确返回。

### ISSUE-001：静态文件路由越界读取

**类型**：安全缺陷 · **范围**：HTTP、静态文件 · **优先级**：P1 · **状态**：已修复（2026-10-19，本地 HTTP 验收；线上部署未核验）

#### 现象与影响

修复前，控制台构建存在时，未鉴权的 `/ui/{path:path}` 路由可以将路径解析到静态目录之外。进程可读的配置、凭据或租户数据可能被下载，具体可访问范围取决于运行账户权限和文件路径。

#### 原因与证据

原处理器将请求路径直接拼入 `_DIST`，只检查文件是否存在，便交给 FileResponse；没有拒绝绝对路径、父目录跳转，也没有验证最终真实路径仍在构建目录内。

初始证据验证编码父目录能匹配该路由，返回目录外文件的 FileResponse，状态为 200。此次回归先用临时合成文件通过 HTTP TestClient 复现原实现返回 200；修复后增加真实本机 Uvicorn HTTP 请求，验证编码父目录与反斜杠路径返回 404，正常页面和资源可完整传输。不涉及真实凭据或用户记忆，线上部署未核验。

#### 修复与验证

`/ui`、`/ui/*` 与 assets 统一经过 StaticFiles。解码后的非法路径直接拒绝，realpath + commonpath 阻止目录外链接；仅合法且缺失的页面地址回退到经过相同边界检查的 index.html，缺失 assets 返回 404。构建状态按请求检查，未构建时全部控制台入口返回 503。

覆盖正常资源、许可文件、GET/HEAD、安全响应头与真实 Windows junction。文件符号链接的三项回归在本机因权限不足跳过，支持符号链接的平台继续执行。命令、原始日志及验证边界见[静态目录边界验收](../results/ui_static_boundary_validation.md)。

#### 处理要求

使用具备目录边界检查的静态文件服务，或在解码后拒绝非法路径并校验 realpath 的目录包含关系。边界检查须覆盖符号链接，不能仅根据文件存在性或字符串前缀判断；单页应用的正常深路径仍应回退到 index.html。

#### 验收标准

- 编码父目录、绝对路径、不同平台路径分隔符及指向目录外的链接均不能读取目录外文件。
- 通过实际 HTTP 请求验证拒绝行为，仅使用合成文件，不读取真实配置或租户正文。
- 正常资源、许可文件、GET/HEAD、SPA 深路径和未构建提示仍可用，安全响应头保持有效。

**代码与证据**：[静态路由](../mnemotrace/server/app.py)、[HTTP 回归](../tests/test_ui_static.py)、[验收入口](#evidence-issue-001)。

### ISSUE-002：旧目录回退造成命名空间串读与误删

**类型**：安全缺陷 · **范围**：租户隔离、存储、擦除 · **优先级**：P1 · **状态**：已修复（2026-10-19，合成隔离验收；线上部署未核验）

#### 现象与影响

修复前，若命名空间 B 的 ID 等于命名空间 A 的安全目录名，B 的旧目录候选就与 A 的存储目录重合。读取 B 可以返回 A 的事实；清空 B 可以删除 A 的存储，即使调用者只操作被授权的 B。

调用者需要能使用 B 这个逻辑命名空间：开放模式允许直接选择 namespace，静态鉴权模式取决于租户 ID 配置。此问题不等同于已经证明可绕过 API key 鉴权。

#### 原因与证据

原实现中，`_safe_user(A)` 生成的名字也满足 `_legacy_safe_user(B)` 的规则。`_path(B)` 可回退到 A 的安全目录，`forget(B)` 会将该目录加入删除候选。检查路径仍在数据根目录内，不能证明路径属于正确租户；按逻辑 user 分离的锁也不能隔离重合的数据目录。

合成复现中，两个不同 namespace 解析到同一目录，B 能读取 A 的标记事实；清空 B 后重新加载 A，事实数量为 0。复现只操作临时目录与合成数据。

#### 修复与迁移

- 按所有者决定彻底取消运行时旧目录回退。`_path` 始终返回当前 namespace 的摘要目录，`forget` 也只删除这一目录；删除 `_legacy_safe_user` / `_legacy_paths`，不再保留命名例外或旧候选集合。
- 顶层路径必须保持原始目录项名称，拒绝指向同级命名空间的链接，以及 Windows 大小写/尾点别名；拒绝时不接管或擦除链接目标。
- 所有旧目录及旧 `.pkl` 候选均不被服务读取、写入或清空；它们存在时，新写入仍只进入摘要目录。确需保留旧内容时，管理员应停止共享数据目录的进程并备份，核验真实归属后，显式复制到该 namespace 自己且尚不存在的摘要目录，验证后再处理旧来源。不得仅凭目录名推断归属。
- 既有摘要目录名和 JSONL/manifest 格式不变；共享此数据目录的全部 HTTP/MCP/写入进程应升级并重启。

MemoryService 的读取、写入、清空、同/异服务实例并发、重启和已鉴权 HTTP 见[仅摘要目录验收](../results/digest_only_namespace_validation.md)。随后补齐本地批量导入 CLI，统一经 MemoryService.import_ 使用相同目录与事务锁，见[CLI 验收](../results/import_cli_digest_validation.md)。最初的保留名排除方案仅作为[历史记录](../results/namespace_ownership_validation.md)，已被取消旧目录回退的方案替代。

#### 处理要求

- 运行时仅使用摘要目录，不保留旧目录读取或擦除候选。
- 读取和 forget 使用相同的安全路径规则；不能仅修改默认读路径而保留跨租户删除候选。
- 明确发生所有权冲突时的拒绝与迁移规则，不以静默合并、重写或删除数据解决冲突。

#### 验收标准

- 覆盖 B 等于 A 的安全目录名、B 已有独立安全目录，以及目录和旧 pickle 候选重合的情况。
- B 的读取、写入、并发操作及擦除均不能访问或破坏 A；重启后结果一致。
- 旧目录始终不被服务读写或删除，需要其内容时仅允许管理员确认归属后显式迁移；路径穿越、链接保护与擦除锁隔离仍有效。

**代码与证据**：[命名空间路径与擦除](../mnemotrace/service.py)、[串读与误删复现](#evidence-issue-002)。

### ISSUE-033：并发加载旧快照导致写入丢失

**类型**：缺陷 · **范围**：服务缓存、并发、存储 · **优先级**：P1 · **状态**：已修复（2026-10-20，Windows/Ubuntu CI 验收；线上部署未核验）

#### 现象与影响

读取旧快照期间，另一请求完成写入并保存。较慢的读取随后将旧对象放入缓存，却登记为新版本；后续读取不会重载，下一次保存可能覆盖已经成功写入的内容。

问题发生在同一命名空间内，与 ISSUE-002 的目录串读不同。以上为修复前的路径，修复已通过 Windows/Ubuntu 双平台 CI 验收。

#### 原因与证据

修复前 MemoryService.get 在锁外调用 Memory.open，完成后才读取 manifest 版本并更新缓存。加载的内容与登记的版本可能不属于同一次保存，旧加载也可以覆盖另一请求刚更新的热缓存。逐集合加载还可能混合两次保存的内容，单独给缓存发布加锁不足以解决。

先前的合成调度与本轮真实 Windows 文件系统均复现了“新增记录保存成功、缓存回到旧内容、下一次保存丢失新增记录”的顺序；另复现了清空后的缓存回填及重新保存复活旧事实。

#### 已实施修复与验收边界

- 按稳定锁路径共享进程内可重入线程锁和文件锁所有权；读取的线程锁覆盖完整操作，冷加载的文件锁覆盖全部集合读取及缓存发布。写入、迁移和清空使用同一协议。
- manifest 新增可选 `snapshot_id`；加载对象携带实际读到的提交令牌，旧格式使用 manifest 原文摘要。写入前校验对象归属及基准令牌，拒绝旧对象回写。
- 嵌套读取固定本次对象，返回业务数据与缓存引用分离。默认内存索引的热读可以读取上一份已提交缓存，不等待另一进程尚未提交的同步写入。
- Windows manifest 读取允许共享删除，并用原生 ReplaceFileW 原子替换已有 manifest，避免热读句柄使提交失败。独立 Memory 的并发读改存和中途崩溃恢复仍在本项范围外。
- 本地 Windows 原生验证与可重复命令见[统一访问协议验收](../results/issue033_034_validation.md)。提交 `9bb7395` 已通过 Windows/Ubuntu、Python 3.10/3.12 四组 CI；[运行记录](https://github.com/NotZhu/MnemoTrace/actions/runs/39378499937)与[原始 CI 证据](../results/issue033_034_ci_validation.jsonl)可追溯。

#### 验收标准

- 固定上述交错顺序，成功写入在后续读取、再次保存和重启后均保留。
- 覆盖首次加载、版本变化重载、同/异服务实例和真实跨进程并发。
- 不引入重复取锁，不使 forget 后的旧对象重新成为当前缓存。

**代码与证据**：[缓存加载与版本](../mnemotrace/service.py)、[共享锁协调](../mnemotrace/_namespace_lock.py)、[快照读写](../mnemotrace/store/persist.py)、[真实文件回归](../tests/test_service_transactions.py)、[验收原始日志](../results/issue033_034_validation.jsonl)、[修复前合成复现](#evidence-issue-033)。

### ISSUE-034：自动重嵌入在写入路径重复取锁

**类型**：缺陷 · **范围**：服务锁、重嵌入 · **优先级**：P1 · **状态**：已修复（2026-10-20，Windows/Ubuntu CI 验收；线上部署未核验）

#### 现象与影响

已有存储与当前 embedder 不匹配、且开启 MNEMOTRACE_REEMBED_ON_MISMATCH 时，首次访问若来自写请求，会重复获取同一命名空间的文件锁，等待自身释放，阻塞该请求及后续同空间写入。

普通读取入口没有外层写锁，因此不能用读取迁移成功证明写入入口也正常。POSIX 已有这一隐患，新增 Windows 文件锁后也需要覆盖。

#### 原因与证据

修复前写接口先进入 write_lock，再调用 get。get 捕获维度或模型身份不匹配后，重新打开同一锁文件并进入 _user_file_lock；外层锁须等 get 返回才能释放。

合成锁桩及本轮 Windows 原生锁均确认重复获取会阻塞。旧重嵌入测试只从 memories 触发，未覆盖首次写入或后台 worker。

#### 已实施修复与验收边界

- 迁移只在已持文件锁的加载函数内执行，完成重嵌入和保存后再发布缓存。嵌套调用复用最外层的文件锁句柄，跨实例同线程读取也使用相同路径的锁协调对象。
- 维度和模型身份不匹配均覆盖 read、remember、add_fact、import 和 async worker/flush；使用可终止子进程限时验证，检查迁移后磁盘内容、向量与重启读取。
- 补充关闭迁移、迁移失败不发布缓存、并发迁移保留两次写入等回归。Windows 本地与 Windows/Ubuntu、Python 3.10/3.12 四组 CI 已通过，详见[统一访问协议验收](../results/issue033_034_validation.md)及[原始 CI 证据](../results/issue033_034_ci_validation.jsonl)。

#### 验收标准

- 维度和模型身份不匹配分别覆盖首次读取、remember、add_fact、import 及异步整合。
- POSIX、Windows 原生锁下均能限时完成，迁移后重启可读，事实与原文完整。
- 开关关闭时仍拒绝不兼容存储；并发迁移不覆盖正常写入。

### ISSUE-035：退出或切换账号后旧导出仍下载

**类型**：缺陷 · **范围**：控制台、导出 · **优先级**：P2 · **状态**：已修复（2026-10-20，本地合成回归与前端构建；真实浏览器及线上部署未核验）

#### 现象与影响

修复前，账号 A 发起完整导出后退出或登录 B，A 的迟到响应仍会触发下载，内容可能包含 A 的私密原文。
页面卸载不会停止异步下载或全局 toast 回调。

#### 原因与证据

导出绕过普通 JSON 请求的凭据检查；认证状态也只有 Key，无法区分同一账号的不同登录周期。
因此仅补 Key 比较仍会接受 A→退出→A 的旧响应，旧 401 还可能退出重新登录的 A。
查询清理订阅跳过直接同 Key 登录，偏好异步回写也只检查 Key，均存在相同的周期缺口。

修复前导出 10 个场景全部失败；共享请求保护加入后，另确认查询／偏好 5 项和页面提示／页面树 5 项行为回归失败，
再分别修复至通过。网络、下载、指纹和 React hook 使用合成边界，不包含真实用户数据或文件下载。

#### 已实施修复与验收边界

- 认证 store 每次登录／退出原子推进内存 epoch；请求捕获 `{key, epoch}`，普通 JSON 与导出共用成功和失败路径的会话检查，过期以 `StaleSessionError(409)` 拒绝。
- 响应和正文完成后及下载前检查归属；提示前再核对一次，取消不显示成功或失败。URL 与下载元素在 finally 中清理；已触发的下载不追溯撤销。
- 查询按 epoch 取消和移除，回调同时检查周期与缓存对象；偏好延迟激活／回写检查快照，已登录页面树按 epoch 重建。公共 `/health` 请求及缓存保留。
- 本地前端完整测试 190 项通过，查询隔离入口 81 项、演示登录 12 项、偏好 14 项及生产构建通过。新增回归已纳入现有 CI 入口，尚未声称远端 CI 或真实浏览器验收。
- 本次只取消客户端尚未执行的后续动作；请求已抵达服务端时仍可在 A 的空间完成，不撤销已发送的写入，不证明曾绕过服务端鉴权。

#### 验收标准

- 等待响应或读取 Blob 时退出、A→B、A→退出→A、A→B→A、直接同 Key 登录，旧导出均不触发下载。
- 正常完整／精简导出可用，异常路径正确释放资源；旧 401 不退出新登录，取消不产生错误横幅或 toast。
- `/health` 跨登录变化仍可完成；同 Key 新周期移除旧缓存，延迟偏好修改不跨周期生效。

### ISSUE-033：旧加载覆盖新缓存，再次保存丢失成功写入

4. 下一次写入从热缓存追加 next-write，再保存。

```text
disk_after_successful_write: ['old', 'saved-by-writer']
hot_cache: ['old']
cache_tag: (2, 1)
disk_after_next_write: ['old', 'next-write']
```

以上为修复前的合成结果，disk 为列表模拟的保存介质，cache_tag 为模拟版本。本轮已补充真实
